# 客服回覆一致性與回饋整理規則

最後更新：2026-09-16

本文件是客服建議轉成 AI 回答、線上知識資料與回饋追蹤狀態的現行契約。修改知識庫、路由提示、固定 SOP 或重跑回饋案例前，先閱讀 `active_customer_service_handoff_2026-09-14.md` 與本文件。

## 1. 維護原則

- 客服建議定義的是客戶應得到的答案，不是只供人工判讀的備註。已確認的建議要轉成可測試的回答契約。
- 客戶明確提出的服務主體、操作目的與上一輪使用者訊息優先；不可被相似文件、其他系統台、舊 AI 錯答或廣泛方案資料帶偏。
- 已有明確主題與客服處置時，不可回覆「沒有足夠明確資料，請換個方式描述」。只有主題真的無法判定時，才可澄清。
- 客戶看到的回覆不可出現 HTML 標籤、內部 API、帳務系統等術語。連結使用可點選連結，不輸出 `<a ...>` 原始碼；需身分核對時使用「登記電話」。
- 事實資料（價格、活動、適用系統台、有效期限、頻道、網址、營業時間）維護在線上知識來源；回答順序、身分／安全限制、工具呼叫門檻維護在程式與本文件。不得把會變動的費率或活動內容寫死在 router prompt。

## 2. 已確認回答契約

### 回答範圍

- 使用者只問一個明確欄位時，只回答該欄位；例如「客服電話多少」只能回答公司名稱與客服電話，不可加上地址、營業時間、服務地區、優惠、內部資料或其他連結。客服電話、地址、營業時間、服務地區與官網應直接使用公司資訊欄位，不經 RAG 摘要。

### 繳費、發票與收據

- **線上繳費**：只問線上繳費時，回答官網與行動客服 APP 的線上流程，不改答 ibon 等實體繳費。官網依序為：官方網站、線上繳費、用戶編號與密碼、選擇信用卡／ATM 等方式、依提示完成。APP 依序為：下載並登入、勾選待繳帳單、立即繳費、選擇線上刷卡／LINE Pay 等方式、依提示完成。提醒線上刷卡、ibon、FamiPort 繳費會自動開通，完成後關閉設備電源再重開機。
- **APP／官網繳費後的實體收據或發票**：先明確說明不會另外寄送實體收據到府；入帳後於營業日以簡訊通知發票號碼。再提供官網「客戶服務 → 發票查詢 → 輸入客編及密碼」與 APP「註冊登入 → 用戶資訊」查詢路徑。
- **發票開立時間**：電子發票於入帳後第二天以簡訊通知；紙本發票通常於入帳後 16 天內寄出。依客戶問題補充官網歸戶流程，不可把載具流程取代主要問題。
- **發票歸戶到手機條碼**：使用者直接問「發票可以載具嗎／發票可以載具」時，視為完整的載具歸戶問題，直接依序引導「官網 → 線上繳費 → 帳號密碼登入 → 用戶歸戶 → 用戶歸戶2 → 財政部網站」，不可先回資料不足或交給 RAG 摘要。使用者說「發票加入手機條碼」但尚未明確問操作時，只問「請問您是想將發票歸戶到手機條碼載具嗎？」。客戶確認或明確問操作時，提供相同官方流程。不可在聊天中索取手機條碼、手機號碼、驗證碼或證件資料。
- **已繳費要求復線**：只接受清楚、完整的超商繳費收據圖片。OCR 必須同時能辨認超商繳費收據格式與三段條碼，才可呼叫收據復線 API。禁止接受使用者手動輸入三段條碼；圖片不完整、收據來源不明或條碼不清楚時，只請客戶重新上傳完整收據。
- **便利商店無法繳費**：優先引導 ibon／FamiPort 機台操作；只有條碼失效、金額不符、列印失敗等明確交易異常才轉帳務確認。

### 真人客服與資料安全

- 使用者只說「轉真人」、「找真人客服」或「不想跟 AI 講」而未說明服務問題時，先回覆「可以，請先告訴我遇到什麼問題，我會先協助確認；若仍需要真人客服，我會提供轉接方式。」；此時不可輸出真人客服連結，也不得說「請稍後」或承諾等待時間。
- 使用者在上述澄清後說明具體服務問題、同一則訊息已說明問題且仍要求轉接，或系統已明確判定該帳務／設定事項需真人處理時，WEB／external API 必須提供可點選的真人客服轉接連結。
- 真人客服、資料變更或其他需核對帳戶的服務，不得要求客戶在聊天中提供不必要個資；若需要說明核對資料，使用「登記電話」等對外用語。
- **合約與目前方案**：僅限已登入的 WEB 會員請求明確帶入客編時查詢。WEB 訪客、LINE 使用者與聊天中自行輸入客編者，一律不查詢，也不可改收戶名與電話；固定回覆「為保障您的個人資料安全，個人帳務及方案等資訊需登入會員後才能查詢，您可以至官網或行動客服 APP 登入後查看相關資料。」查詢本期待繳帳單、網路復線與電視復線則例外：訪客可提供客戶編號、戶名、登記電話任兩項。

### 方案、頻道與服務異動

- **裝機申請三類入口**：「有線電視裝機申請」只進純有線電視流程；「網路裝機申請」只進純網流程；「同時申裝有線網路」、「有線電視+網路裝機申請」及同義問法只進電視＋網路同裝流程。第三類只可顯示正式的同裝活動資料，並排除純網與社福方案；不可落入泛用網路裝機回答或輸出整份活動文件。未指定服務類型的「裝機申請／申裝優惠」先詢問這三類。
- **優惠方案**：每一則優惠問題先由 LLM 判斷服務類型、具名方案與是否需要澄清；廣泛問題不得由關鍵字規則直接回覆三選一。未指定服務類型時，LLM 回覆「有線電視＋網路、純網路、純有線電視」三選一，不直接列出混合方案。選定有線電視＋網路時只檢索同裝方案；選定純網路時只列純網方案的名稱、服務類型、速率與活動期間，排除電視加網路與社福方案；選定純有線電視時只檢索基本收視費與裝機費資料，排除寬頻同裝方案。客戶點名特定方案時，第一輪只列「寬頻費用、贈品、裝機費、違約金」；綁約、繳別、設備、加購、抽獎與其他限制，等客戶明確追問才說明。已介紹具名方案後，客戶只回「對／是／好」時，LLM 只澄清要追問哪個欄位，不得重送整份活動。低收入戶／中低收入戶／身心障礙等社福優惠只能在客戶明確提及資格時檢索或說明，不得在一般優惠回覆中主動列出。
- **活動資料動態性**：活動名稱、別名、有效期間、速率、費用、贈送內容與條款只維護在有 `current` 狀態與有效日期的知識文件。優惠入口的 router prompt 與服務範圍選項檢索字串只能描述服務類型與需要的資料欄位，不得寫入任何具名活動方案。名稱容錯只可對目前索引文件的 `campaign_name` 與 `campaign_aliases` 進行高信心比對；活動下架或改名後重新索引即可生效，不需改程式。
- **優惠輸出與延遲**：LLM 完成意圖判斷後，方案清單與具名方案首答由已檢索文件的結構化欄位組成短答；不再為這兩種已完整命中的情境追加 LLM 證據重排或全文摘要。方案清單只可採用同時具備 `campaign_name` 與 `document_type=promotion_campaign` 或 `record_type=campaign_*` 的資料；不得以 FAQ 標題、LINE TV 說明或一般知識文件充當方案名稱。客戶選擇「網路裝機申請／純網路」或「有線電視＋網路裝機申請」後，第一輪先按方案列出方案名稱，以及最多三組「速率＋對應繳別金額」；活動期間可另列一行。裝機費、押金、點數、抽獎、設備賠償與其他條款不可混入這一輪，待客戶點名方案或追問欄位再回答。清單最多四項，每個方案獨立成編號區塊；純網清單不重複顯示服務類型。不使用分號或把全部欄位塞入括號。系統必須保存當輪實際顯示的動態方案順序；客戶下一輪回覆編號或完整方案名稱時，須對回同一份檢索結果並進入該方案首答，不可回覆無法理解、重列整份清單或以一字容錯蓋過完全相符的名稱。清冰組、贈送頻道與機上盒的內容只在客戶明確詢問時，依檢索結果局部回答，不得在純網方案清單後自動附加固定說明。
- **清冰組**：清冰組為申裝純網方案的客戶額外贈送的電視頻道。申裝該方案可免費借用 1 台聯網機上盒，每戶最多 1 台且無法另外付費加裝；約有 20～24 個頻道，實際頻道依公司安排可能異動。此資料以獨立知識文件維護，不寫入優惠 router prompt，也不綁定任何會下架的活動名稱。只問機上盒時只答台數與加裝限制；只問頻道數時只答頻道數與異動說明。
- **基本頻道**：簡短回答基本頻道為有線電視頻道，並引導至所屬系統台官網的最新頻道表；不可貼出方案內容或回覆資料不足。
- **數位套餐加購**：先依客戶是否使用聯網型機上盒區分；聯網型可依指定流程自行加購，非聯網型由客服處理。客戶已指出套餐名稱時，不可回問成 LINE TV、哈 TV 或其他服務。
- **機上盒密碼／未授權**：畫面要求密碼時先輸入預設密碼 `0000`。輸入後出現「未授權」時，先說明可能誤切到加購付費頻道；200 台以後通常需另行訂閱，請按頻道向下鍵切換到一般收視頻道。
- **第四台及光纖更換用戶**：第一輪固定回答「【申請方式】資料未提供『第四台及光纖更換用戶』的具體流程或應備文件，需由客服依帳戶與合約狀態確認。」不可擅自補方案、違約金、設備、帳務或個資要求。
- **退租／退租計算**：先確認服務類型，並依客服建議回答契約、設備與合約資訊處理；不可因後續追問而遺失前一輪已確認的服務主體。

## 3. 線上知識資料更新規格

客服只要提供原始 CSV Q&A 即可；系統可以產生檢索別名與分類，但不能自行發明公司事實。會變動或需要精準篩選的資料，應改以可維護的結構化表單／CSV 欄位儲存。

每筆正式知識至少要有：

| 欄位 | 用途 |
| --- | --- |
| `title` / `question` | 客服可理解的主題或標準問法 |
| `answer` | 已確認、可直接對外的事實或 SOP |
| `service_type` | 例如寬頻、有線電視、帳務、發票、設備 |
| `company_scope` | 通用或適用系統台 |
| `status` | `current`、`retired`、`deleted` |
| `effective_from` / `effective_to` | 活動、費率、公告或期限性資料必填 |
| `official_url` | 有官網操作頁或正式表單時填入 |

- `current` 可主動推薦與回答；`retired` 不主動推薦，但原用戶或明確點名時可查；只有錯誤／不得保留資料才用 `deleted`。
- 更新線上資料後必須重新索引，才能更新 ChromaDB 的舊 chunk。
- 同一答案的不同問法應由系統產生檢索別名，不應讓客服複製多份相同 Q&A；別名只能改善命中，不得加入新費率、新資格或新流程。
- 客服建議改變的是流程或安全邊界時，先更新本文件與程式測試；改變的是價格、活動、網址或營業資料時，先更新線上知識來源與有效日期。

## 4. 回饋追蹤狀態

| 顯示狀態 | 儲存狀態 | 意義與下一步 |
| --- | --- | --- |
| 待修正 | `pending` + `pending` | 尚未完成修正或尚未有可驗證回答。 |
| 待整理 | `processed` + `organizing` | 已有修正或重跑資料，但因資料整理、規則整併或 token 限制暫停；不可當作驗收通過，runner 會略過。 |
| （追蹤清單不顯示） | `processed` + `merged` | 已併入另一筆代表案例，不再計入待整理或顯示為追蹤項目；原始回饋只保留供追溯，不代表驗收通過。 |
| 待驗收 | `processed` + `pending` | 已重跑，等待逐筆比對客服建議。 |
| 驗收通過 | `processed` + `passed` | 客服建議、服務主體、必要步驟與限制均已確認一致。 |
| 驗收退回 | `pending` + `failed` | 不符合客服建議，需先分析路由、檢索、知識或工具邊界後修正。 |

「拉取線上資料」必須同時同步新增回饋、對話、處理紀錄與追蹤狀態。追蹤狀態以 `updated_at` 比較，只套用較新的線上資料，不得用舊狀態覆蓋新狀態。

2026-09-16 起，因測試 token 費用限制，已修正但尚未驗證的批次先改列「待整理」。此狀態不會被 `scripts/rerun_pending_acceptance_cases.py --all-open` 重新呼叫 API。

同類回饋整理時，只保留一筆代表案例為「待整理」，其餘來源改列「已合併來源」。代表案例可重寫成較清楚的使用者情境，客服口語建議則轉成可驗收的專業回答契約；合併來源不得刪除或誤標為驗收通過。

恢復驗證時依序執行：更新線上資料或規則 → 重新索引（如有知識變更）→ 將個案改回「待驗收」→ 以新 token 重跑 → 逐筆比對客服建議 → 標記通過或退回。不可直接將「待整理」改成「驗收通過」。
