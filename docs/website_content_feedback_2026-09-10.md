# 智能客服介紹網站修改回饋

- 檢查網址：https://delicate-dragon-6f9561.netlify.app/
- 網站標題：客製化智能客服服務 - 台灣基礎開發科技
- 檢查日期：2026-09-10
- 文件用途：提供網站文案、設計與前端製作者安排修改。
- 檢查範圍：依本次瀏覽取得的頁面內容、表單屬性與可見介面整理；未實際送出聯絡表單，也未驗證後端收件、正式部署設定及全部互動流程。

## 整體評價與修改方向

網站已具備完整的產品介紹脈絡，從客服誤答痛點、雙引擎架構、實例對照、服務工具，到多通路、後台管理與安全控管，能協助企業理解產品價值。建議保留這個主架構。

本次修改重點是讓網站達到可正式交給潛在客戶的狀態：補齊資料、確認洽詢能送達、讓功能宣稱符合實際交付範圍，並確保展示入口與頁面說明一致。

優先順序定義：

- P1：正式對外推廣前應完成。
- P2：建議同步改善，可提升理解與洽詢意願。
- 待確認：目前證據不足，需由製作者或產品負責人確認，不能直接當作已證實的故障。

## P1：正式對外前應修改

### 1. 清除所有「待填」內容

**觀察到的問題**

頁面仍含以下占位文字，會讓客戶覺得網站尚未完成：

- `〔待填：解決率〕`
- `〔待填：秒數〕`
- `〔待填：天數〕`
- `〔待填：企業服務專線〕`
- `〔待填：業務聯絡信箱〕`
- `〔待填：服務時間〕`
- `〔待填：地址〕`
- `〔待填：回覆時間〕`
- `〔待填：實測數據〕`

**修改建議**

聯絡資訊請填入正式資料。解決率、回覆速度與導入天數如尚無可核實資料，先移除對應數字或區塊，改用已能確認的功能價值。不要以估計值包裝成實測成果。

如需呈現成效數據，請補上測試期間、樣本量與計算方式；導入天數則應註明適用範圍與必要條件。

**驗收方式**

全站搜尋「待填」，確認無殘留；所有聯絡方式由業務確認可用，所有量化宣稱均有資料依據。

### 2. 確認聯絡表單確實能送達

**觀察到的問題**

目前讀取到的表單屬性如下：

| 項目 | 觀察值 |
| --- | --- |
| action | 網站首頁網址 |
| method | GET |
| form name | 未設定 |
| Netlify 表單標記 | 未觀察到 |
| 收集欄位 | 公司、聯絡人、電話、Email、同意勾選等 |

若表單採用瀏覽器原生送出流程，GET 會將填寫資料帶入網址查詢參數，可能留在瀏覽紀錄或相關存取紀錄中。僅憑這些屬性，尚不能證明表單有接上實際收件服務。

**待確認**

是否存在 JavaScript 攔截送出並呼叫 API 的實作。本次未送出表單，因此不能直接認定收件功能失效。

**修改建議**

確認並完成實際的收件流程，可使用既有後端或 Netlify Forms。使用適合的 POST 提交方式，避免將聯絡資料放入網址；若採用 Netlify Forms，請依部署設定完成表單識別與收件驗證。

補齊送出中、成功、失敗及重試狀態，避免重複送出。失敗時保留已填資料，成功時應等到收件服務確認後才顯示成功訊息。

**驗收方式**

由製作者使用測試資料送出一次，確認指定後台或信箱有收到完整內容；網址不含聯絡資料。再測試必填欄位、Email 格式、未勾同意及網路失敗情況。

### 3. 調整功能上線與交付範圍的宣稱

**觀察到的問題**

頁面出現「已上線」、「已經實際運作」、「導入後即可使用」等說法。若未註明適用環境，客戶容易理解成所有列出的功能都能在自己的系統直接使用。

依目前專案整理，部分流程仍需客戶端 API 串接、啟用或正式環境驗證，不適合一律視為可立即交付。

**修改建議**

每項服務依實際狀態標示，以下文字可供替換，但使用前需由產品負責人確認事實：

| 實際狀態 | 建議說法 |
| --- | --- |
| 已在既有環境驗證 | 既有導入環境已支援，實際交付依客戶系統與串接範圍確認。 |
| 已具備工具介面，但需接客戶系統 | 可依客戶 API 串接後啟用。 |
| 目前是模擬或展示流程 | 展示流程，正式服務需完成系統串接與驗證。 |
| 尚未完成的需求 | 可評估客製開發，範圍與時程另行確認。 |

以下項目應優先核對，確認前建議標示為「可串接後啟用」，避免寫成全面上線：

- 真實報修工單建立與取消報修。
- 新申裝代辦。
- 服務地址可申辦查詢。
- 實際加值服務申辦。

帳務查詢、補寄帳單、繳費條碼、復通等工具，也應說明需具備對應 API、身分驗證與客戶授權條件。

**驗收方式**

產品與工程逐項確認功能清單，每項皆能對應可展示或可交付的實作；展示情境與尚待串接項目有明確標示。

### 4. 避免對 AI 回答做絕對保證

**觀察到的問題**

「唯一依據」、「一律有出處」、「不憑空生成」等說法過於絕對。知識檢索、工具限制與回答規則能降低誤答風險，但應依實際機制描述，避免讓客戶理解成保證零錯誤。

**建議替換文字**

| 原說法 | 建議說法 |
| --- | --- |
| 唯一依據 | 以企業提供的知識內容與授權系統查詢結果為主要回答依據。 |
| 一律有出處 | 可依回答類型與系統設定，提供來源或查詢依據。 |
| 不憑空生成 | 透過知識檢索與工具權限控管降低無依據回答的風險；資訊不足時可引導補充資訊或轉接人工。 |

上述替換文字中的來源顯示、追問及轉接，也需確認實際支援範圍後使用。

**驗收方式**

檢查全文是否仍有「保證」、「完全」、「一律」、「零錯誤」等無充分依據的承諾；對外文案應能對應實際控制機制。

### 5. 讓客服體驗入口與文案一致

**觀察到的問題**

頁面引導訪客使用「右下角的智能客服對話視窗」，但本次檢查未看到可操作的客服入口。右下角觀察到的是 Netlify 標記。

**待確認**

客服元件是否有延遲載入、網域限制、裝置限制、同意條件或部署設定尚未完成。

**修改建議**

完成元件載入與互動驗證。若目前尚未提供公開試用，將該段改為「預約展示」，並連到聯絡表單。

**驗收方式**

以未登入的新瀏覽工作階段，在桌面與手機開啟網站，確認入口可見且能收發訊息；若改為預約展示，確認按鈕可到達表單，並移除所有「右下角對話視窗」的引導。

## P2：建議同步改善

### 6. 釐清九個品牌的實績與架構能力

「九個獨立品牌同時在跑」容易被理解成九個品牌均已正式上線營運。若目前證據僅是內建九個品牌或系統台資料，建議改為：

> 支援多品牌與多系統台設定，目前已建置九個品牌／系統台的資料架構；實際導入範圍依專案確認。

若確有正式營運實績，請確認可公開範圍後，再使用上線數量與案例資訊。

### 7. 釐清 APP 是既有入口或選配整合

「同一套知識庫，三個入口」若包含尚需整合的 APP，建議改為：

> 支援 Web 與 LINE，並可透過 API 延伸整合至企業 APP。

APP 區塊標示「可選配整合」或「需串接」，使訪客能區分目前支援與專案擴充範圍。

### 8. 在首屏提供明確的洽詢按鈕

主標題「讓客服聽懂問題，而不是比對關鍵字」可保留。建議在旁邊提供清楚的「預約展示」或「洽詢導入」按鈕，連到聯絡表單。

若有可公開使用的客服展示，再加入「體驗智能客服」入口。按鈕文字與實際動作應一致。

### 9. 整理正式對外的品牌呈現

建議正式推廣時採用品牌網域，並確認目前右下角 Netlify 標記是否為預期顯示。若可依部署方案設定移除，建議移除，避免與客服入口混淆。

頁面上的公司名稱、頁尾資訊、隱私權政策與聯絡窗口應一致。現有隱私權政策連結也請確認是否適用於此網站與表單。

### 10. 驗證 FAQ 與行動版互動

本次未完整測試所有 FAQ 展開內容及手機版排版，以下列為驗收項目，不代表已確認存在故障：

- FAQ 展開後有完整答案，鍵盤也能操作。
- 導覽錨點可到達正確區塊，標題不被固定導覽列遮住。
- 手機上的比較表、服務項目與表單不溢出畫面。
- 客服入口、固定標記與表單按鈕不互相遮擋。

> 預約展示，了解企業知識問答、服務工具與真人轉接如何配合您的客服流程。
