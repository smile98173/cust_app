# 客服 AI 現行交接紀錄

最後更新：2026-09-16

本文件記錄近期與需求方確認的客服 AI 架構、回饋修正與知識庫維護原則。新 task 開始時應先閱讀本文件，再修改路由、帳務或知識庫行為。

客服建議已整理成可維護的回答契約與線上資料更新規格，詳見
`customer_reply_alignment_2026-09-16.md`。該文件列出的具體客服回答、真人轉接、收據驗證與優惠摘要規則優先於較早的歷史紀錄。

## 1. 核心架構原則

- 每一則客戶訊息必須先由 LLM 判斷意圖、流程、工具與知識檢索需求。不得以快速關鍵字路由直接產生客服答案。
- `run_intent_router()` 是正式入口；正常路徑不使用 `fallback_router()` 的舊規則回答。
- LLM 路由無法使用或無法輸出有效 JSON 時，固定回覆：`系統暫時無法判讀您的需求，請稍後再試。`
- Guard 只可做結構性保護，例如阻擋不存在的工具；不得以關鍵字覆寫 LLM 的有效意圖或直接回答客戶。
- 客戶前一輪助理回答可能是錯誤回覆。判斷上下文時優先採用近期使用者訊息，不可讓先前錯答污染新一輪意圖。

## 2. 檢索與回答保護

- RAG 結果不是答案。LLM 先判讀意圖後，才依服務主體、所問欄位與系統台檢索。
- 明確服務主題必須有同主題證據才能進摘要器。目前已加題意證據閘門，涵蓋移機／搬遷、退租、固定 IP、線上繳費與 YouTube 等，避免例如「移機」被低收入戶優惠文件壓過。
- 證據審核模型若明確判定文件不足以回答，該批文件不得被硬拿來回答。資料不足時應澄清或轉真人，不可答非所問。
- 不同服務不得混答：有線電視、寬頻網路、電視加網路、LINE TV、Wi-Fi 加值、聯網機上盒、數位套餐均為不同服務主體。
- 使用者詢問線上繳費時，應維持官網／行動客服 APP 的線上繳費脈絡，不得改答 ibon 等實體通路；使用者明確詢問繳費方式時才列出可用管道。

## 3. 已確認的客服規則

- 退租：未說明服務類型時，先問有線電視、寬頻網路或兩者皆退。電視為機上盒及配件；網路為數據機及配件，不能混用。
- 數位頻道加購：先確認機上盒是否聯網。聯網機上盒可自行加購；非聯網機上盒需由客服處理。
- 方案推薦：依客戶目前速率推薦更高一階；電視加網路用戶優先推薦同類型，除非客戶明確問純網路。升級前需確認原方案與合約，實際資格及費用依查詢結果。
- 500M／方案價格：不得在 prompt 寫死活動名稱、費率或方案。需由目前有效知識文件取得。
- YouTube：是聯網型／雙模機上盒功能與換裝需求，不是不存在的獨立 YouTube 加值服務；不可錯答未提供服務或直接要求查合約。
- 停用客編、帳務資料、復線與繳費結果，必須以實際 API 回傳及既有轉譯規則為依據。

## 4. 帳務 API 邊界

- 未經需求方明確允許，不得修改 CUST／帳務 API 的商業規則、原始訊息解讀或規則轉譯。
- 可修正對外用語，使其不暴露「帳務系統／API」等內部術語；可使用「登記電話」等客戶用語。
- 帳務類回饋先說明 API 原始回覆與目前轉譯，再由需求方決定是否調整。

## 5. 知識庫維護方向

### 一般 FAQ

- 客服可維持最小 CSV：`問題,答案`。
- 匯入流程應自動產生檢索別名、常見口語／錯字、分類、服務實體與向量；自動產生內容僅用於檢索，不得新增公司規則、費率或流程。
- 同答案的不同問法應是同一正式文件的別名，不應讓客服複製多份相同 Q&A。

### 結構化表單

適合結構化而非一般 FAQ 的資料：優惠活動、數位套餐／頻道、設備與功能、服務異動 SOP、公司公告、申請表單／連結、費率、頻道異動。

優惠活動已有 `promotion_campaign` 解析：系統可從活動文件自動抽取方案名稱、別名、服務類型、速率、綁約、繳別、適用客群、有效期間、贈品、抽獎、申請方式與限制。後續應讓客服只確認少數必要欄位：

- 系統台範圍
- 是否目前可申辦
- 有效期間
- 下架後是否仍保留給原用戶查詢
- 專用申請表單（如有）

### 方案生命週期

- `current`：可主動推薦與新申辦。
- `retired`：不可主動推薦；原用戶、API 查到舊方案、或客戶明確提方案名稱時仍可查內容，回答須說明已下架。
- `deleted`：錯誤或不應保存資料，才從索引永久移除。
- 從目前活動 CSV 移除時，預設應移入 `retired` 歷史索引，不可直接抹除，避免既有客戶查不到原方案內容。
- 通用裝機／維修申告網址放公司資訊；特定活動的專用申請表單才放活動記錄，並帶有效期限與系統台範圍。

## 6. 回饋與 API 回歸

- 真實驗證必須使用 `D:\AI智能客服\env\.env.ai-test`，以 `/api/auth/token` 取短效 token，呼叫 `http://127.0.0.1:8123/api/v1/chat`。
- Token 約 15 分鐘；批次 runner 必須每筆獨立更新 token。
- `scripts/rerun_pending_acceptance_cases.py` 可使用：
  - `--feedback-id`：指定案例，不受追蹤狀態限制。
- `--all-open`：重跑待修正與待驗收全部開放案例。
- `review_status=organizing`（追蹤頁顯示「待整理」）的案例已暫停 API 重測與驗收；runner 會自動略過，僅在明確移回「待驗收」後才可重跑。
  - `--resume-json`：從 checkpoint 接續，只略過已成功的案例。
- 測試回答不得在未人工／模型品質判讀前直接回寫追蹤器。可用 `scripts/publish_rerun_conversations_to_tracker.py` 僅更新修正後對話，不能改狀態。

### 2026-09-14 全量批次狀態

- 開放案例：218（84 待修正、134 待驗收）。
- 正在使用 8123 外部 API 續跑，checkpoint：`reports/pending_acceptance_api_rerun_20260914_161459.json`。
- 長多輪案例可能超過 2 分鐘；API 暫時逾時標記為 `ERROR`，主批次完成後必須以 checkpoint 重試，不能視為最終失敗。
- 批次結束後順序：重試 ERROR → 依客服建議品質判讀 → 修正可確認問題 → 全量再跑 → 回寫最新已驗證對話。

### 2026-09-16 暫停驗證狀態

- 因測試 token 費用限制，已修正但尚未重新驗證的案例移入「待整理」，不代表驗收通過。
- 恢復時必須先依 `customer_reply_alignment_2026-09-16.md` 更新線上知識或規則，再以新 token 重跑、逐筆對照客服建議，最後才可移回「待驗收」或「驗收通過」。

### 回饋驗收契約

- 「API 回覆成功」不等於「案例通過」。每筆案例必須將原始使用者對話、新 AI 回覆與客服建議一起比對。
- 只有新回覆符合客服建議的核心意圖、服務主體、必要步驟與限制時，才可列為待驗收或驗收通過。
- 不符合時必須先分類原因：LLM 意圖／上下文、檢索證據、知識庫缺漏、工具 API 原始訊息，或帳務既有轉譯；再決定修正位置。
- 知識庫缺漏與帳務商業轉譯不可由系統自行編造或改寫，須列為待客服補件或待需求方確認。
- 完成可修正項目後，必須重新執行所有開放案例，發布的是最後一輪已驗證回覆，不是第一輪測試輸出。

## 7. 禁止事項

- 不可自行修改客服上傳的知識庫 CSV 或編造缺少的公司資料；缺資料要列出請客服補充。
- 不可把促銷方案名稱、費率、活動期間硬寫入 router prompt。
- 不可因帳務 API 回覆看似不合理而自行推定客戶狀態。
- 不可因 RAG 只命中相似文件就回答；題意不符即視為無有效證據。
